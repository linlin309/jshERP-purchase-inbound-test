## 二、执行方式

所有命令在 `api-tests/` 目录、虚拟环境激活后执行。

| 目的 | 命令 |
|---|---|
| 默认安全集（不含真实写操作） | `pytest` |
| 冒烟 | `pytest -m smoke` |
| 单个文件 | `pytest tests/test_contract.py` |
| 单条用例 | `pytest tests/test_contract.py::test_depot_head_list -v` |
| 按关键字 | `pytest -k depot_head -v` |
| 只收集不执行 | `pytest --collect-only -q` |
| 生成 HTML 报告 | `pytest --html=reports/report.html --self-contained-html` |
| 生成 Allure 报告 | `pytest --alluredir=reports/allure-results`，再 `allure generate …`（见第五节） |
| 写操作用例（M3，5 条） | `pytest -m write`；执行前需单独授权，串行跑 |
| 配置类用例（M4 起才有） | `$env:RUN_CONFIG_TESTS=1; pytest -m config` |
| 权限类用例（M5 起才有） | `pytest -m permission` |

说明：

- `pytest.ini` 中 `testpaths = tests`，在 `api-tests/` 下直接运行 `pytest` 即可，不需要指定路径。
- `reports/` 目录不入库，生成前若不存在需要先创建：`New-Item -ItemType Directory -Force reports`。
- 单条与单文件运行时，默认 `-m` 仍生效；`tests/test_write_inbound.py` 带 `write` 标记，单文件运行需显式加 `-m write`，否则会被默认过滤。

## 三、marker 与默认过滤

`pytest.ini` 定义了四个 marker：

| marker | 含义 | 默认 |
|---|---|---|
| `smoke` | 只读冒烟，不创建业务数据 | 执行 |
| `write` | 会创建或修改业务数据 | 排除 |
| `config` | 会切换全局配置 | 排除，且需 `RUN_CONFIG_TESTS=1` |
| `permission` | 需要受限用户 | 排除 |

默认 `addopts` 是 `-m "not write and not config and not permission"`。命令行传入 `-m` 会覆盖它，例如 `pytest -m smoke` 只跑冒烟，`pytest -m write` 只跑写操作。

`--strict-markers` 已开启：拼错 marker 名会直接报错，不会静默当成未标记用例执行。

`pytest -m write` 只是按 marker 筛选用例，**不构成业务写操作的授权**。是否执行写接口、造多少数据、怎么清理，必须由使用者单独授权；授权之前，即使 marker 已经存在也不执行。

写用例的硬性前提：

1. `forceApprovalFlag="1"`：否则库存变动时机不同，W03–W05 会跳过库存断言；
2. `updateUnitPriceFlag="0"`：否则建单会改写商品采购价，全部写用例跳过；
3. 串行执行，不使用 `-n` 等并行插件；运行期间不要在前端对同一商品+仓库做出入库；
4. 执行前记录运行时间，结束后按 `API-` 前缀 + 时间戳检查是否有残留。

## 五、报告与结果判读

| 结果 | 含义 | 优先看什么 |
|---|---|---|
| `passed` | 断言全部成立 | — |
| `failed` | 契约或行为不符 | 断言消息里的接口路径、业务码、响应体 |
| `skipped` | 前置数据不足 | 跳过原因，必要时补数据后重跑 |
| 退出码 2 | 后端不可达 | 启动 9999 后重跑，不是用例失败 |

报告：

```powershell
New-Item -ItemType Directory -Force reports | Out-Null
pytest --html=reports/report.html --self-contained-html
```

- `reports/` 不入库；分享前检查报告是否带账号信息。

Allure 报告（M2.3 起）：

```powershell
pytest --alluredir=reports/allure-results
allure generate reports/allure-results -o reports/allure-report --clean
allure open reports/allure-report
```

- `allure-results` 是原始数据，`allure generate` 才产出可浏览的 HTML；两者都在 `reports/` 下，已被忽略。
- 需要本机安装 Allure CLI（当前 2.38.1）。未安装时 pytest 照常运行，只是没有 Allure 报告。
- 报告按 `suite` 分组：基础冒烟 / 接口契约 / 鉴权与会话 / 异常与边界；标题带 04 的用例编号；A05 展示 5 个执行步骤。
- `--alluredir` 不写进 `pytest.ini` 的默认参数，避免空跑或筛选运行也产生产物。
- 失败排查顺序：后端是否启动 → token 是否有效（`loginOut`）→ 前置数据是否存在 → 参数是否齐全。

## 六、接口守卫

执行时有两道检查，缺一不可：

1. **事前拦截**：`client.py` 按 `READONLY_CALLS` / `SESSION_CALLS` / `WRITE_CALLS` 三类登记接口，未登记或写接口未带 `allow_write` 时在发出前抛 `RuntimeError`，不会到达后端。
2. **事后核对**：会话结束时打印

   ```text
   [接口守卫] 本次共 33 次接口调用（只读 32 / 会话操作 1 / 写操作 0）
   [接口守卫] 全部命中已登记接口
   ```

   若出现未登记调用，会打印具体请求并把退出码改为 1。注意它只是核对，不代替事前拦截。

确认本轮没有写数据，看三处：

- 输出中有「全部命中已登记接口」，且「写操作 0」；
- 没有 `RuntimeError`；
- 运行前后同一查询的总数一致，例如 `/depotHead/list?subType=采购` 的 `total` 不变。

新增只读接口时，先确认没有写副作用，再加入 `READONLY_CALLS`；写接口只能进 `WRITE_CALLS`，且只有 `write_client` 能发。

退出登录（`GET /user/logout`）作为**会话操作**单独登记在 `client.SESSION_CALLS`：不进 `READONLY_CALLS`，也不绕过统一 client。守卫按三类分别统计，A05 用独立 client 执行退出，不污染共享会话。

## 七、写用例的清理与恢复

`created_bill` fixture 在用例结束后清理，顺序固定：

1. 用 IF-07 列表按单号查询并做**精确过滤**；查不到 → 视为已清理；
2. 查到且已审核 → `batchSetStatus 0`，重新查询确认状态回到未审核；
3. 反审核失败或状态仍不是未审核 → **停止**，不假定可以删除；
4. 未审核 → `delete`；
5. 删除接口明确成功后复查主表（按单号精确过滤）和明细（按 `headerId`）；原会话遇到 `HTTP 500 loginOut` 时，用独立只读客户端重新登录复核；两项都为空才算清理成功。

任何一步查询失败、响应结构不符、状态不明，或独立会话重新登录/复查失败，都算清理失败，报错信息包含单号、状态、接口、HTTP 状态和响应体。后端已知行为：同一用户同一 IP 在同一秒内产生两次「单据」操作日志时会强制退出；写请求按 2 秒间隔发送（跨用例换 client 也生效），独立会话复查作为兜底保留。常见残留按以下步骤恢复：

1. 前端单据列表按单号搜索 `API-` 开头的单；
2. 若为已审核，先反审核；若反审核被拒（采购状态变化），记录单号与提示，不要强删；
3. 反审核成功后删除；
4. 仍无法处理时保留单号和完整响应，不要直接用 SQL 改 `delete_flag`。

## 八、故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 退出码 2，提示"无法连接后端" | 9999 未启动 | 启动 jshERP-boot 后重跑 |
| HTTP 500，正文 `loginOut` | 未登录或 token 已失效 | 检查 `client` 是否登录成功；A 组用例会主动构造该状态 |
| `code=300`，`数据查询异常` | 缺 `subType` 等未捕获异常 | 对照 02 的请求要点补齐参数 |
| `code=8500007` 等业务码 | 业务校验未通过 | 对照 02 与 04 的预期，不要把业务码当 HTTP 错误 |
| 大量 `skipped`，提示前置数据不足 | 演示环境缺数据 | 补数据后重跑，不要当通过 |
| `RuntimeError: 不在只读白名单…` / `需通过 write_client` | 调用了未登记接口，或用共享 client 发写请求 | 只读接口确认无副作用后登记；写请求改用 `write_client` |
| 登录失败 `RuntimeError` | 账号、密码或 MD5 处理有误 | `.env` 存明文，MD5 由 `client.py` 完成 |
| 验证码导致登录失败 | `checkcode_flag` 被打开 | 当前基线为 0，本阶段不测试验证码，也不要自行改配置 |
| 写用例批量跳过 | `forceApprovalFlag` / `updateUnitPriceFlag` 前置不满足 | 按跳过原因处理；读数方法见 02 的 IF-21，不改配置 |
| 退出码 5，显示 no tests collected | marker 筛选后没有用例（当前 `-m config`） | 正常现象，不代表执行失败，也不代表拿到写权限 |

## 九、新增一条用例

1. 在 [04-接口测试用例](04-接口测试用例.md) 增加编号与字段，写清前置、步骤、预期、清理。
2. 在 `tests/test_<组>.py` 增加测试函数，只通过 `client` 发请求。
3. 成功路径用 `assert_ok`；预期失败用 `assert_business_error(resp, code)`，必须写明期望业务码。
4. 写业务数据一律使用唯一 `API-` 单号，清理由 `created_bill` fixture 终结器或 `finally` 执行；该规则不构成写权限。
5. 运行对应 marker，确认新用例与全量用例都通过。
6. 回填 04 的「实现位置」「状态」，同步 02 的验证状态；接口有变化时先改 02。
7. 提交代码、用例与文档。

## 十、维护约定

- **编号不复用**：删除的用例保留编号并标「已废弃」，新用例继续往后排。
- **接口变更**：先改 02，再改用例与断言，最后跑全量；不要只改断言让用例变绿。
- **用例废弃**：删除测试函数，保留 04 的记录，状态改「已废弃」。
- **文档分工**：接口变化改 02，框架变化改 03，用例增删改 04，执行方式变化改 05。
- **不放宽断言换通过**：预期确实变了，写进 04 的变更记录，并说明是行为变化还是契约变化。
- **不为了统计改代码**：跳过与通过的区别由前置数据处理保证，不用额外逻辑美化报告。
