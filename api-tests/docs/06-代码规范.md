# 06 - 代码规范

> 状态：M3（2026-11-10）
>
> 适用范围：`api-tests/` 下全部 Python 代码、测试用例与文档
>
> 相关：[03-框架设计与骨架](03-框架设计与骨架.md)、[02-接口清单](02-接口清单.md)

本规范基于现有代码整理，不是外部模板的照搬。PEP 8 / PEP 257 / pytest 官方实践只取与当前项目相关的部分，目标是让下一个人（或者 AI）读一眼就知道该怎么写。

## 一、语言、缩进与布局

- Python 3.12，统一使用 `api-tests/.venv`，不装全局包。
- 4 空格缩进，不用 Tab；文件末尾留一个空行；不在行尾留空格。
- 一个文件一个职责：`config.py` 管配置、`client.py` 管 HTTP、`conftest.py` 管 fixture、`utils/` 管通用工具、`tests/` 只管用例。
- 代码行尽量不超过 100 字符。中文断言消息（`f"账户结构不符: {data}"`）不强行拆行，可读性优先。
- 模块名 `snake_case`，类名 `PascalCase`，函数与变量 `snake_case`，模块级常量 `UPPER_SNAKE_CASE`（如 `READONLY_CALLS`），fixture 用 `snake_case` 名词（`client`、`demo_data`）。
- 不用拼音缩写；`dh`、`mvo` 这类是上游 jshERP 的命名，本项目不沿用。

导入顺序，三组之间空一行：

```python
import json            # 标准库
import pytest          # 第三方

from client import ErpClient        # 本项目，绝对导入
from utils.assertions import assert_ok
```

- 项目内一律绝对导入（`from client import ...`），不用相对导入。
- 按名字导入具体对象，不 `import *`。
- 不在导入阶段做网络请求、登录或读环境变量之外的副作用；`config.py` 的 `load_dotenv()` 是目前唯一的模块级副作用，保留。

## 二、注释与 Docstring

- 默认不写注释。只在“代码看不出来的原因”处写一行，中文。
- 注释写约束和坑，不写“这里在做什么”：

```python
# subType 必传：不传会在 getBillCategory 抛 NPE，返回 code=300 数据查询异常
search = json.dumps({"type": "入库", "subType": "采购"}, ensure_ascii=False)
```

- Docstring 只给“公共且需要解释行为”的函数：`utils/assertions.py` 的断言函数、`conftest.py` 的两个私有辅助（因为失败与跳过的区别是约定）、fixture 的用途。
- 私有函数名以下划线开头（`_json_body`、`_need_list`、`_need_id`），能说明意图就不写 docstring。
- 测试函数不写 docstring，用例标题就是它的说明；需要背景时用一行注释写“为什么测这个”。
- 禁止逐行翻译代码、禁止留下没有归属的 `TODO`。已知限制写在 docs 里，不写在代码里。

## 三、函数设计

以下几条是判断信号，不是硬性门槛；以“读得懂、改得动”为准，明显偏离时再说明理由：

- 一个函数一件事。测试函数通常在 30 行左右，明显超出时先看是不是一次判定了太多东西，再决定拆还是保留。
- 相同逻辑出现第 3 次左右再抽成函数；1–2 处直接写开往往更清楚。`_need_list` / `_need_id` 是这样抽出来的，`assert_ok` 也是。
- 参数在 4 个左右时用 dict 传（`demo_data` 就是这个形态）；更多时先想“是不是该拆函数”，而不是造配置类。
- 不为单个用例建类、建工具模块或加参数开关。`utils/data.py` 是 M3 写用例的公共构造/查询/清理工具；`utils/db.py` 等 M4 真需要再加。
- 返回值保持平台原样：能返回 `resp` 就不包装成自定义对象，能返回 dict 就不转成 dataclass。

## 四、异常处理

- 不写裸 `except:`，不写 `except Exception: pass`。吞异常等于隐藏失败。
- 只在真正的边界捕获：`conftest.client` 捕获 `requests.ConnectionError` 转成 `pytest.exit(..., returncode=2)`，把“后端没起”和“用例失败”分开。
- 接口返回的业务错误用断言表达，不用 `try/except` 包住请求。预期失败就走 `assert_business_error`。
- 不自己发明异常类型；需要中断整轮时用 `pytest.exit`，需要跳过用 `pytest.skip`。
- 清理逻辑（M3 起的写用例）由 fixture 终结器或用例的 `finally` 执行，用例失败也会触发；失败信息里带单号和响应，避免制造无法解释的残留数据。

## 五、pytest 用例

- 文件按域拆：`test_smoke.py`（冒烟）、`test_contract.py`（契约）、`test_auth.py`（鉴权）、`test_exception.py`（异常）、`test_write_inbound.py`（写流程）、`test_write_support.py`（写支撑模拟）。
- 函数名 `test_<被测行为>`，用英文动词短语，一个函数只判定一个结论。
- marker 只有四个，含义写在 `pytest.ini` 里：

| marker | 用途 | 默认 |
|---|---|---|
| `smoke` | 只读冒烟 | 执行 |
| `write` | 会创建/修改业务数据 | 排除 |
| `config` | 会改全局配置 | 排除，且需 `RUN_CONFIG_TESTS=1` |
| `permission` | 需要受限用户 | 排除 |

- fixture 作用域按需：`client`、`demo_data` 是 session 级，因为登录和数据解析只该做一次；用例私有的准备数据用函数级 fixture。
- fixture 不修改全局状态、不写业务数据。共享 fixture 只放“读了不会变”的东西。
- 参数化只在“同一段逻辑、不同入参”时使用（`@pytest.mark.parametrize`）；预期不同的场景写不同用例，不要用参数化拼出“半个用例”。
- 用例之间互不依赖、与执行顺序无关；默认 28 条安全用例单独跑、全量跑、只跑 smoke 都必须通过，5 条写用例在授权后单独运行。
- 断言失败信息要能定位：带接口路径、业务码、响应体或单号。

## 六、接口请求与统一 Client

- 所有请求经 `client`：`client.get/post/put/delete`。测试里不 `import requests`、不 `client.session.get(...)`、不自己拼 URL。
- `login()` 也在 `client` 内部完成，用例不关心 token。
- 新增接口先确认有没有写副作用，再往 `client.READONLY_CALLS` 里加 `(method, path)`。加不进去就说明它不该在当前阶段跑。
- `WRITE_CALLS` 只登记写接口，不授权执行；发写请求必须用 `write_client`（`allow_write=True`），共享 `client` 始终保持只读。
- 白名单是默认拒绝：新增 GET 也要显式放行，不按方法粗粒度放行。
- `client` 只负责发送和记录，不做业务断言；断言在用例里，工具在 `utils/assertions.py`。
- 写用例必须带 `write` marker；marker 只筛选用例，不等于授权。

## 七、断言设计

分三层，按顺序：

1. **HTTP 状态**：`assert_ok` 已包含“HTTP 200 + `code==200`”，不要自己再写一遍。
2. **业务码**：成功用 `assert_ok`；预期失败用 `assert_business_error(resp, code)`，必须写明期望码。
3. **结构与关键字段**：类型、必填字段、数量关系（`total >= len(rows)`、`pageSize` 生效）。

约定：

- 只锁契约里稳定的东西，不锁提示文案、不锁时间、不锁自增 id。
- 成功响应不等于副作用发生（删除不存在的 id 也返回成功形态），涉及状态变化的判定必须查详情或列表。
- 数值用 `isinstance(x, (int, float))` 且排除 `bool`；`tests/test_contract.py` 里的 `_number()` 就是这条的落地写法，新增用例沿用。
- 断言消息写“哪里不符 + 实际值”，不写“断言失败”。

## 八、测试数据管理

- 动态获取，不硬编码 id、条码、账户。`demo_data` 从 IF-03/04/02/07/15/05 取值。
- 取数失败分两类，必须区分：
  - **结构不符**（不是数组、缺 `id`、缺 `barCode`）→ 断言失败，这是契约问题；
  - **列表为空** → `pytest.skip("前置数据不足：…")`，写明缺什么，不算通过。
- 写操作用例（M3）用 `API-<yyyyMMddHHmmss>-<6 位十六进制>` 单号，创建后必须能清理；清理由 `created_bill` fixture 在 `yield` 后执行，W02 这类不建正常单据的场景用 `finally`。
- **单号与清理规则只是 M3 的写法约定，不构成写权限**：任何新增/修改/删除业务数据都必须由用户单独授权，并说明造数范围与清理方式。规范里出现写接口的名字，不等于允许调用它们。
- 判断单据是否还在：主表用 IF-07 列表按单号精确过滤，明细用 IF-15 按 `headerId` 查询；删除后两项都为空才算清理成功。查询失败或结构不符按清理失败处理，不能当成“已删除”。
- 不直接改数据库的 `delete_flag`、库存、业务日期；数据库只读，且只用于查询核对（M4 才引入）。
- 用例不能依赖上一条用例造的数据。

## 九、敏感信息与测试数据安全

- `.env` 不入库；`.env.example` 只放占位符。
- 不打印 `PASSWORD`、token、完整请求头；断言消息只放业务字段。
- 报告（`reports/`）不入库，分享前先检查是否带账号信息。
- 贴日志时只贴接口路径、状态码、业务码和脱敏后的响应。
- 演示账号和飞书链接属于个人学习项目的公开信息，可以出现在根 README 和 docs 中；生产凭证一律不出现。

## 十、依赖管理与代码复用

- 依赖只加在 `requirements.txt`，用版本区间（`pytest>=8,<9`），不锁死小版本。
- 加依赖前先问“标准库或已有依赖能不能做”。当前只有 pytest、requests、python-dotenv、pytest-html、allure-pytest。
- 按阶段引入：PyYAML 暂不引（`.env` 够用），PyMySQL 只读查询 M4 再引；Allure 已在 M2.3 引入（`allure-pytest`），只做报告分组与标题，不挂附件。
- 不引入 Ruff、Black、isort、mypy 等工具链，格式靠本规范和评审；确实需要时单独提，不和功能改动混在一起。
- 复用顺序：现有 `client` → 现有 fixture → `utils/assertions.py` → 再考虑新增。不为一条用例改公共工具。

## 十一、改动的完成标准

一次改动算完成，需要同时满足：

1. `pytest -m smoke` 和 `pytest` 都能通过，或者失败原因已写清楚；
2. 没有新增写接口调用、没有触碰数据库和环境配置；
3. 受影响文档同步：接口变化改 `02`，框架变化改 `03`，用例新增改 `04`；
4. 汇报里写真实结果，包含失败输出，不写“应该没问题”。
