## 一、文档说明

### 1.1 定位

本文件只描述接口层的测试用例。它与根目录 `docs/测试文档/04-测试用例.md` 的 43 条手工用例是**两个独立体系**：

- 手工用例验证界面上的完整业务流程，判定对象包含页面渲染、按钮显隐、交互提示，接口层无法替代；
- 本文件的用例验证接口契约、鉴权边界、异常返回，以及主链路中可读取的观测面；
- 两者需要时互相引用业务目标（例如"验证审核后库存变化"），但不做逐条映射，也不为了对齐而拆分用例。

### 1.2 测试范围

| 范围 | 说明 |
|---|---|
| 读接口 | 基础资料、单据、明细、库存、进销存、序列号、系统配置 |
| 会话 | 登录、会话校验、退出登录及其后果 |
| 写接口 | **当前不覆盖**，M3 起按 `write` marker 单独执行 |

当前阶段的硬约束：默认执行不产生任何业务数据；会话操作（退出登录）在独立 client 中执行，不影响共享会话。

### 1.3 编号规则

格式 `API-<组字母><两位序号>`，按测试层分组，不按业务模块分组。

| 组 | 含义 | 状态 |
|---|---|---|
| S | Smoke，基础冒烟 | 已启用 |
| C | Contract，接口契约 | 已启用 |
| A | Auth，鉴权与会话 | 已启用 |
| E | Exception，异常与边界 | 已启用 |
| F | Flow，业务流程 | 保留，见 §7 |
| T | sTate，状态流转 | 保留，见 §7 |
| D | Data，数据一致性 | 保留，见 §7 |
| G | confiG，配置开关 | 保留，见 §7 |
| P | Permission，权限 | 保留，见 §7 |

约定：

1. 组内序号递增，**只追加、不复用**。删除的用例保留编号，状态改为「已废弃」。
2. 一条用例对应一个独立测试目标。实现上可以是一个测试函数、一个参数化的多组入参，或一条包含多步断言的场景；不要求一个函数一条用例。
3. 编号在文档与 Allure 标题中维护：代码函数名不带编号，`@allure.title` 以「编号 + 名称」显示，两处需保持一致。
4. 新增流程：先在本文加编号和字段，再写代码，最后回填「实现位置」与状态。

### 1.4 用例字段

| 字段 | 必需 | 说明 |
|---|---|---|
| 编号 / 名称 | 是 | 名称用动词短语，能直接当报告标题 |
| 测试目标 | 是 | 这条用例要证明什么，一句话 |
| 接口 | 是 | 对应 [02-接口清单](02-接口清单.md) 的 IF 编号与路径 |
| 前置条件 | 是 | 逐条编号、一行一条 |
| 测试步骤 | 是 | 请求与参数写全，编号列表 |
| 预期结果 | 是 | HTTP 状态、业务码、结构、关键字段，编号列表 |
| 实现位置 | 是 | `文件::函数`，未实现写「待实现」 |
| 状态 | 是 | 见 §1.5 |
| 优先级 | 建议 | P0 主链路 / P1 契约 / P2 边界 |
| 阶段 / 只读性 | 建议 | 阶段用于排期；只读性区分只读、会话操作、写业务数据 |

执行标记（`smoke` / `write` / `config` / `permission`）统一登记在 §8 的实现索引，不在每条用例里重复。

### 1.5 状态定义与执行边界

| 状态 | 含义 |
|---|---|
| 已实现·通过 | 测试函数存在，断言完整，最近一次执行通过 |
| 已实现·仅外层结构 | 测试函数存在，只断言外层形状，字段细节留待后续收紧 |
| 待实现 | 预期已明确，代码未写 |
| 待验证 | 预期尚未实测，不能当作契约 |
| 已废弃 | 保留编号，测试函数已删除 |

执行边界：默认 `pytest` 只执行不含 `write`、`config`、`permission` 标记的用例。本文 A 组中除 A05 外均为普通只读；A05 属于会话状态操作，不改业务数据，随默认执行。

## 二、核心业务链路

### 2.1 采购入库完整流程

业务主线是采购入库的完整生命周期，原文见 [01-需求规格](../../docs/测试文档/01-需求规格.md) 第九章：

> 建单取号 → 选供应商与结算账户 → 确认日期 → 加明细（仓库、商品、数量、单价）→ 自动算金额与价税合计 → 填本次付款 →（可选）关联采购订单、上传附件 → 保存（未审核，库存变化）→ 审核（已审核）→ 反审核 → 删除（库存回退）

两点需要写清楚，避免误读：

- 这条主线是**正常路径加反审核、删除两个异常分支**，不包含全部业务变体。关联采购订单、多账户付款、序列号/批号商品、多单位、强审核开关，都是挂在主线上的分支场景。
- 主线描述的是业务动作，不是接口调用顺序。界面上的一步可能对应多个接口，也可能没有接口。

### 2.2 接口视角的链路拆分

| 段 | 业务动作 | 接口 | 接口性质 | 阶段 |
|---|---|---|---|---|
| 0 服务与鉴权 | 打开系统、登录 | IF-01、IF-13 | 读 / 会话 | M2 |
| 1 基础资料 | 选供应商、结算账户、仓库、商品 | IF-02、IF-03、IF-04、IF-05 | 读 | M2 |
| 2 单据查询 | 列表、按单号或 id 看主表、明细、关联单 | IF-07、IF-08、IF-14、IF-15、IF-20 | 读 | M2 |
| 3 库存观测 | 按仓库和条码查库存、进销存 | IF-12、IF-17 | 读 | M2 |
| 4 建单保存 | 取号、填表头与明细、保存 | IF-06 | 写 | M3 |
| 5 审核 / 反审核 | 批量改状态 | IF-10 | 写 | M3 |
| 6 修改 / 删除 | 编辑、删除、批量删除 | IF-09、IF-11、IF-16 | 写 | M3 |
| 7 一致性核对 | 单据、明细、库存、序列号互相对照 | IF-12、IF-15、IF-17、IF-18 | 读 | M3–M4 |
| — UI 段 | 进入页面、前端自动取号、关联订单弹窗、附件上传 | 无对应接口 | — | 手工 |

第 1–3 段在业务上是"选择"和"查看"，在接口上是查询；第 4–6 段是写；第 7 段是读，但依赖第 4–6 段先产生数据。

### 2.3 当前阶段覆盖范围

M2 覆盖第 0–3 段的**只读观测面**。它能证明：

1. 服务可访问，登录可用，会话可校验；
2. 主链路依赖的基础资料（供应商、账户、仓库、商品）可查询且结构可用；
3. 已存在的采购入库单可通过列表、详情、明细读取；
4. 库存与进销存可读取，可作为后续写用例的观测手段。

它**不能证明**，也不在文档里宣称：

1. 采购入库单可以成功创建；
2. 保存后库存发生变化；
3. 审核与反审核正确；
4. 删除后库存正确回退。

这四项要等 M3 执行写操作后才能验证。

### 2.4 后续阶段覆盖规划

- M3 接第 4–6 段：建单、审核、反审核、修改、删除，以及它们的必然失败路径。
- M3–M4 接第 7 段：单据、明细、库存、序列号的一致性核对；M4 起引入只读数据库查询作为旁证。
- 分支场景（关联采购订单、多账户、序列号/批号、多单位、强审核）在 M3 开工时再确认纳入范围，本文不预先设计用例。
- UI 段不做接口自动化，由手工用例覆盖。

## 三、S｜基础冒烟

### 3.1 测试目标

判断"服务起来了、登录成立、基础资料读得到"。它是最小可用性检查，不覆盖完整链路，也不替代 C 组。

### 3.2 用例

**API-S01 登录后会话可用**

- 测试目标：登录成功后，携带 token 能取得当前用户会话。
- 接口：IF-01 `POST /user/login`（由 `client` fixture 完成）、IF-13 `GET /user/getUserSession`
- 优先级 / 阶段：P0 / M2
- 只读性：只读
- 前置条件：
  1. 后端 9999 与演示租户可用；
  2. `.env` 中的账号密码可登录。
- 测试步骤：
  1. fixture 登录并保存 token；
  2. 带 token 请求会话；
  3. 检查返回的 `data.user`。
- 预期结果：
  1. HTTP 200，`code=200`；
  2. `data.user` 为对象；
  3. `data.user.loginName` 非空。
- 实现位置：`tests/test_smoke.py::test_login_and_session`

### 3.3 缺口记录

按 §2.2 第 0–3 段核对，冒烟未覆盖五个接口：供应商（IF-02）、按条码取商品（IF-05）、单据列表（IF-07）、单据详情（IF-08）、库存（IF-12）。

它们已由 C 组覆盖结构，因此**体系不缺验证，缺的是快速失败入口**：基础资料或单据查询坏掉时，冒烟仍是绿的。

若后续扩展，从 S04 起编号，本轮不实施。

## 四、C｜接口契约

### 4.1 测试目标

锁定只读接口的响应形状、关键字段与类型，不锁提示文案、时间戳和自增 id。分两级：

- **强契约**：字段存在且类型正确，后续建单与核对会直接依赖；
- **结构校准**：只锁外层形状，字段细节留到对应阶段收紧。

## 五、A｜鉴权与会话

### 5.1 测试目标

证明鉴权边界：登录成功与失败的区分、无 token 与坏 token 被拒绝、退出登录后的状态变化。

### 5.2 用例

**API-A01 登录成功返回 token 与用户信息**

- 测试目标：正确凭证下返回可用的 token 和用户信息。
- 接口：IF-01 `POST /user/login`
- 优先级 / 阶段：P0 / M2.2
- 只读性：只读
- 前置条件：
  1. 后端 9999 可用；
  2. `.env` 中账号密码正确。
- 测试步骤：
  1. 提交 `{loginName, password: md5(明文), code: "", uuid: ""}`；
  2. 检查 `data.token`、`data.msgTip`、`data.user`。
- 预期结果：
  1. HTTP 200，`code=200`；
  2. `data.msgTip` 为 `user can login`；
  3. `data.token` 非空；
  4. `data.user.loginName` 与请求一致。
- 实现位置：`tests/test_auth.py::test_login_returns_token`
- 状态：已实现·通过
- 备注：登录失败同样是 `code=200`，成功判定必须看 `data.token`。

**API-A02 错误密码不返回 token**

- 测试目标：错误凭证不会被当成登录成功。
- 接口：IF-01 `POST /user/login`
- 优先级 / 阶段：P0 / M2.2
- 只读性：只读
- 前置条件：
  1. 账号存在；
  2. 使用一个必然错误的密码；
  3. 使用不带 token 的独立 client。
- 测试步骤：
  1. 以错误密码的 MD5 提交登录；
  2. 检查 `data`。
- 预期结果：
  1. HTTP 200，`code=200`；
  2. `data` 中不存在 `token`；
  3. `data.msgTip` 非空。
- 实现位置：`tests/test_auth.py::test_wrong_password_returns_no_token`
- 状态：已实现·通过
- 备注：不锁 `msgTip` 的具体文案。登录接口在入口处会先删除请求头 token 的 `userId`（`UserService.login`），所以**不能用共享 client 发这个请求**，否则即使登录失败也会把共享会话踢下线。

**API-A03 无 token 的受保护接口被拒绝**

- 测试目标：未携带 token 时，受保护接口不会返回业务数据。
- 接口：IF-13 `GET /user/getUserSession`
- 优先级 / 阶段：P0 / M2.2
- 只读性：只读
- 前置条件：
  1. 后端可用；
  2. 能发出不带 `X-Access-Token` 的请求。
- 测试步骤：
  1. 去掉 token 请求会话；
  2. 检查状态码与响应体。
- 预期结果：
  1. HTTP 500；
  2. 响应不是 JSON，正文为 `loginOut`。
- 实现位置：`tests/test_auth.py::test_request_without_token_is_rejected`
- 状态：已实现·通过
- 备注：用 `headers={"X-Access-Token": None}` 去掉共享会话的 token，requests 会删除值为 `None` 的请求头；用例中额外断言该请求头确实未发出。

**API-A04 无效 token 的受保护接口被拒绝**

- 测试目标：伪造 token 无法通过鉴权。
- 接口：IF-13 `GET /user/getUserSession`
- 优先级 / 阶段：P0 / M2.2
- 只读性：只读
- 前置条件：
  1. 后端可用。
- 测试步骤：
  1. 以任意非空字符串作为 token 请求会话；
  2. 检查状态码与响应体。
- 预期结果：
  1. HTTP 500；
  2. 响应为非 JSON，正文为 `loginOut`。
- 实现位置：`tests/test_auth.py::test_request_with_invalid_token_is_rejected`
- 状态：已实现·通过
- 备注：不要用真实 token 截断或变形，避免与 A05 的语义重叠。

**API-A05 退出登录后同一 token 失效**

- 测试目标：验证退出的完整状态变化——退出前有效、退出调用成功、退出后同一 token 被拒绝；同时确认会话按 token 隔离。
- 接口：IF-01 `POST /user/login`、IF-13 `GET /user/getUserSession`、`GET /user/logout`
- 优先级 / 阶段：P0 / M2.2
- 只读性：会话操作（改 Redis 会话，不改业务数据）
- 前置条件：
  1. 主 `client` 已登录，用于验证会话隔离；
  2. 能创建一个独立 client 并单独登录；
  3. 该独立 client 只服务于本用例，执行结束后丢弃，不复用其 token。
- 测试步骤：
  1. 独立 client 登录并取会话；
  2. 同一 client 调用 `GET /user/logout`；
  3. 用同一 token 再次取会话；
  4. 主 client 取会话，确认不受影响。
- 预期结果：
  1. 步骤 1：HTTP 200，`code=200`；
  2. 步骤 2：HTTP 200（实测 `code=400`、`data=null`，该值是 `BaseResponseInfo` 无参构造器的默认值，不作为核心判据）；
  3. 步骤 3：HTTP 500，正文为 `loginOut`；
  4. 步骤 4：HTTP 200，`code=200`。
- 实现位置：`tests/test_auth.py::test_logout_invalidates_token`
- 状态：已实现·通过
- 备注：不得用 session 级的 `client` fixture 调用 logout——它删除的是该 token 在 Redis 中的会话字段，共享 client 一旦退出，后续用例会全部返回 HTTP 500 `loginOut`。A05 必须使用独立 client，执行完丢弃；也不能用 `assert_ok` 判定退出调用，核心判据是步骤 3。
