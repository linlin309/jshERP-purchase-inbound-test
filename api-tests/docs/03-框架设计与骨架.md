## 一、设计原则

- 薄封装：只封装登录、HTTP、断言；不为每个接口写一层类。
- 少抽象：先让 smoke 跑通，M2 再按契约/状态机拆测试文件。
- 配置外置：账号、地址、超时放 `.env`；`.env` 不入库。
- 数据可清理：写操作用例必须有唯一单号和 fixture 清理；M3 前保持只读。
- 失败可定位：断言信息带 HTTP 状态、业务码、响应体；不吞异常。


### 接口守卫（M2.1 起，M3 扩展）

`client.py` 用三个 `(method, path)` 集合登记接口：`READONLY_CALLS`（15 条）、`SESSION_CALLS`（退出登录）、`WRITE_CALLS`（新增/审核/删除）。`request()` 在**发请求前**校验，未登记就抛 `RuntimeError`，请求不会发出去。默认全部禁止，不按“GET 放行 / POST 拦截”粗粒度判断——jshERP 有 POST 只读查询（供应商下拉、序列号列表），也有 GET 会改状态，只能按具体接口放开。

- 写接口还要求实例带 `allow_write=True`；共享 `client` 永远拿不到这个开关，只有 `write_client` 会创建带开关的实例。
- 写请求间隔：带 `allow_write=True` 的客户端每发一条已登记的 `WRITE_CALLS` 请求，距离上一条至少 2 秒（`WRITE_INTERVAL_SECONDS`）；时间戳由所有写客户端共用，跨用例换 client 实例也生效。只读请求和会话操作不受影响。1.1 秒实测仍可能因日志落库点不同而落在同一秒，故取 2 秒。
- `write` marker 只负责筛选用例，**不是请求授权**；把写接口加进 `WRITE_CALLS` 也不等于允许执行，真正跑写用例仍需单独授权。
- 事后兜底：`conftest.pytest_sessionfinish` 复核调用记录并打印“共 N 次（只读 / 会话操作 / 写操作）”，未登记调用会把退出码改成 1。它只是核对，不代替事前拦截。
- 失败的拦截不会计入调用记录（请求未发出）。

### 演示数据（M2.1）

`demo_data` 是 session 级 fixture，动态取数，避免把仓库 14、条码 1001 写成常量：

| 数据 | 来源 | 选取规则 |
|---|---|---|
| 仓库 | IF-03 | `isDefault=true`，否则第一条 |
| 结算账户 | IF-04 | `isDefault=true`，否则第一条 |
| 供应商 | IF-02 | 第一条 |
| 采购入库单 | IF-07（`subType=采购`）+ IF-15 | 列表第一条，明细里取 `barCode` |
| 商品 | IF-05 | 用上一步 `barCode` + 仓库 id 查 |

## 四、配置与环境

`.env` 字段：

| 键 | 必填 | 默认 | 说明 |

| `BASE_URL` | 否 | `http://localhost:9999/jshERP-boot` | 末尾 `/` 会被去掉 |
| `LOGIN_NAME` | 是 | — | 演示账号，见根 README |
| `PASSWORD` | 是 | — | 明文密码；客户端负责 MD5 |
| `TIMEOUT` | 否 | `10` | 单请求超时（秒） |

- `.env.example` 入库，`.env` 不入库（根 `.gitignore` 已配置）。
- `load_settings()` 缺 `LOGIN_NAME`/`PASSWORD` 时直接报错，不静默用空字符串。
- `.env` 只放本机演示账号，不放生产凭证。

## 五、登录与会话

`ErpClient.login()` 发送：

```json
{
  "loginName": "<LOGIN_NAME>",
  "password": "<md5(PASSWORD)>",
  "code": "",
  "uuid": ""
}
```

- **密码必须是 MD5**：前端 `Login.vue` 在提交前做 `md5(values.password)`，后端 `UserService` 直接按 `password` 字段比较。M1 实测用明文 `123456` 得到 `user password error`，改为 MD5 后通过；因此 MD5 放在 `client.py`，`.env` 仍存明文。
- 成功判定看 `data.token`，不能只看 `code=200`：登录失败也是 `code=200`，`data` 为 `{"msgTip":"user password error"}`。
- 拿到 token 后写入 session 的 `X-Access-Token` 请求头；`client` 是 session 级 fixture，一次运行只登录一次。
- 后端不可达时，`conftest.py` 捕获 `requests.ConnectionError`，用 `pytest.exit(..., returncode=2)` 提示先启动 9999，不产生 3 条难读的堆栈。
- 验证码：`checkcode_flag=0` 时 `code`/`uuid` 可为空；若配置被打开，登录需要另行处理，M1 不覆盖。

## 六、断言

M1.1 的断言分两层：

`assert_ok(resp)`：

1. 先看 HTTP 状态，非 200 直接失败（`loginOut` 会显示 HTTP 500 + 响应文本）；
2. 响应必须是 JSON 对象，`body["code"] == 200`；
3. 返回 `body.get("data")`，**不要求 data 一定存在**。IF-06 这类 `standardSuccess()` 成功响应只有 `{code, msg}`，返回 `None`，具体结果由用例查详情/列表验证。

`assert_business_error(resp, code)`：

1. 只接受 HTTP 200；
2. 要求 `code != 200`；
3. **必须传入期望业务码**（如 `8500007`），不符时给出期望值、实际值和响应体；
4. 不把 HTTP 500 当业务错误；`loginOut` 单独按会话/鉴权断言，见 `tests/test_auth.py`。

已知限制：

- 登录失败是 `code=200` + `data.msgTip`，`assert_ok` 仍会通过；登录由 `client.login()` 检查 `data.token`，A 组用例直接断言 `msgTip`。
- 业务错误的数据形态不统一：`data` 可能是字符串（如 `"获取数据失败"`）或对象（如 `{"message": "结算账户不能为空"}`）；用例按实际契约断言，不轻易锁死提示文案。
- 成功响应不等于副作用发生：实测删除不存在的 id 返回 `code=200`、`data.message="成功"`；删除/新增用例必须查详情或列表确认。

## 七、测试数据与清理（M2+）

- 单号：`API-<yyyyMMddHHmmss>-<6 位十六进制>`，避免与手工单号冲突，残留可按 `API-` 识别。
- 新建单据默认 `status="0"`（未审核）；需要审核的用例显式调用 IF-10。
- 清理顺序：反审核（`status=0`）→ 删除（IF-11/IF-16）；放在 `finally`，失败时记录单号和响应，不继续制造新数据。
- M3 实现：`created_bill` fixture 在 `yield` 之后调用 `cleanup_bill`；`finally` 的职责由 fixture 终结器承担，用例失败也会清理。
- 清理前的存在性判断只用 IF-07 列表 + 单号精确过滤：`search.number` 服务端是 `like`，必须在返回行里再按 `number ==` 过滤。查询异常、结构不符、状态不明都算清理失败，**不能当成“单据已删除”**。
- 删除成功后复查两项：主表按单号精确过滤，明细按 `headerId` 查询；原会话遇到 `HTTP 500 loginOut` 时改用独立只读客户端重新登录复核，两项都为空才算清理成功。复查失败保留原错误并提示人工核查。
- 写请求间隔 2 秒（跨用例换 client 也生效），避免同用户同 IP 同秒内的两次「单据」日志触发强制退出；清理时的独立会话复查仍作为兜底保留。
- 库存断言只做前后增量，不做绝对值；同一商品+仓库的写用例串行执行，运行期间不要有手工出入库。
- 写用例前置：`forceApprovalFlag="1"`（否则跳过库存断言）、`updateUnitPriceFlag="0"`（否则跳过整条写用例，避免改商品采购价）。
- 不直接 SQL 改 `delete_flag`、业务日期、库存；数据库只读。
- 配置类用例：先 `GET /systemConfig/getCurrentInfo` 快照 → 修改 → 执行 → `finally` 恢复；串行；需显式 `RUN_CONFIG_TESTS=1`（M4 实现）。
- 权限类用例：M5 准备受限用户；缺失时跳过并写明原因，不用主账号伪造权限结论。
- 数据库断言（M4）：只读 `jsh_depot_head`、`jsh_depot_item`、`jsh_material_current_stock`、`jsh_serial_number`；PyMySQL 只用于查询。

## 八、marker 与执行

`pytest.ini` 已配置：

| marker | 含义 | 当前状态 |
|---|---|---|
| `smoke` | 只读冒烟，不创建业务数据 | 已使用（3 条） |
| `write` | 会创建/修改业务数据 | 默认排除；`pytest -m write` 显式执行，且需单独授权 |
| `config` | 会切换全局配置，串行且需显式开启 | 默认排除；`pytest -m config`，且需 `RUN_CONFIG_TESTS=1` |
| `permission` | 需要受限用户 | 默认排除；`pytest -m permission` |

`pytest.ini` 的默认 addopts 已加入 `-m "not write and not config and not permission"`，所以默认 `pytest` 只收集安全用例；写操作/配置/权限必须显式指定 marker。CLI 的 `-m` 会覆盖 addopts，已用 `pytest -m smoke` 验证。当前有 5 条 write 用例（W01–W05），默认运行全部 deselect；执行需显式 `pytest -m write` 并单独授权。

常用命令：

```powershell
cd api-tests
.\.venv\Scripts\Activate.ps1
pytest                 # 默认只跑安全用例
pytest -m smoke
pytest -m write        # 显式执行写操作
pytest -m smoke --html=reports/report.html --self-contained-html
pytest --collect-only -q
```

`reports/` 不入库；报告里的失败截图/请求体可能含敏感信息，分享前先检查。

## 九、日志与脱敏

- 不打印 `PASSWORD`、token、完整请求头。
- `.env` 不入库；示例值用占位符。
- pytest-html 会记录失败用例的局部变量；M2 起避免把登录响应整体放进断言消息。
- 需要贴日志时，只贴接口路径、状态码、业务码和脱敏后的响应。

## 十、如何新增一条用例

1. 在 `docs/04-接口测试用例.md` 增加 `API-xx`，写清前置、步骤、预期、清理。
2. 在 `tests/test_<组>.py` 增加 `test_...`，使用 `client` fixture。
3. 成功路径用 `assert_ok`；错误路径用 `assert_business_error`，并显式传期望业务码。
4. 写数据用唯一 `API-` 单号；清理由 `created_bill` fixture 终结器或 `finally` 执行。
5. 跑对应 marker（写操作 `-m write`、配置 `-m config`、权限 `-m permission`）；更新 `02-接口清单` 的验证状态。
6. 提交代码、用例文档和必要的接口清单变更。
