## 二、被测对象与测试目标

jshERP 是国产开源进销存 + 财务管理系统，核心业务对象是**单据**。本轮聚焦采购入库单，验证单据从创建到删除的完整生命周期，以及它和库存、权限、校验规则之间的关系。

| 编号 | 目标 | 判定方式 |
|---|---|---|
| G1 | 采购入库的新增、保存、审核、反审核、修改、删除 6 个动作可完整执行，状态流转符合业务预期 | 界面操作 + 数据库状态核对 |
| G2 | 单据数量、金额、库存快照三者的变化可被 SQL 验证，且与业务规则一致 | 操作前后 SQL 对比 |
| G3 | 界面按钮权限与后端接口行为一致，不存在绕过界面的未授权操作 | 低权限账号 + 直接调接口 |
| G4 | 前端校验与后端校验同时存在，绕过前端无法写入非法数据 | 接口层提交非法数据 |
| G5 | 每个结论均附操作步骤、SQL 与证据，第三方可独立复现 | 按文档复跑 |

## 四、测试策略

### 4.1 方法组合

| 方法 | 用途 | 选择理由 |
|---|---|---|
| 手工功能测试 | 主链路操作、界面校验 | 业务规则密集，脚本难以断言"业务上是否正确" |
| SQL 直连对账 | 数量、金额、库存、状态的最终确认 | 界面显示正确不代表数据正确 |
| 接口层测试（Apifox） | 绕过前端、构造边界、验证权限 | 有些场景界面造不出来 |

### 4.2 分层验证

每个验证点按四层留证，便于定位问题出在哪一层：

```
界面操作 → 前端请求 → 后端响应 → 数据库落库
```

### 4.3 证据标准

涉及数量、金额、库存、状态的结论，必须附：**单据号 + 操作前后 SQL 结果 + 时间**。UI 截图不能单独作为数据正确性的证据。

### 4.4 缺陷判定原则

| 情况 | 判定 |
|---|---|
| 代码行为与需求规格明确冲突 | 缺陷 |
| 与合理业务预期冲突，但规格未定义 | 待确认问题，先记录不提交 |
| 配置未开启导致的"异常" | 非缺陷，属配置问题 |
| 上游已公开的安全问题 | 不作为本轮发现，仅在总结中说明 |

### 4.5 缺陷分级

| 级别 | 定义 |
|---|---|
| 致命 | 系统不可用、数据永久损坏、未授权访问 |
| 严重 | 核心功能失效或数据错误，无绕过手段 |
| 一般 | 功能可用但结果不符合预期，有临时规避方式 |
| 轻微 | 文案、提示、体验类问题 |

| 触发条件 | 处理方式 |

## 八、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 配置为租户级，切换影响全局 | 后续用例结论全部失效 | 固定配置执行；确需切换时按组执行，组间恢复并复核 |
| 库存为全局重算，残留单据会污染断言 | 预期值与实际值对不上 | 每步以实测值为准，不拿初始数据当预期；严格执行数据隔离 |
| 需求为逆向整理，可能存在错误 | 用例基于错误需求设计，全部作废 | 执行前先核验需求，存疑项标为待确认 |
| 单人测试，无交叉评审 | 遗漏难以发现 | 用检查清单自查，逐项确认覆盖与预期结果 |
| 上游存在已知安全问题 | 容易误当成自己的发现 | 不复现，仅在总结中说明来源 |
