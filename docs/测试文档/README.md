# jshERP 采购入库 测试文档

> 用途：测试文档正本目录，同时作为飞书知识库的导入源 ｜ 更新：2026-11-09
> 维护方式：先改本目录，复核后再导入飞书；飞书多维表格只维护执行与缺陷。

## 一、目录定位

本目录只放**可对外阅读的定稿文档与证据**，按"需求 → 计划 → 分析 → 测试点 → 用例 → 执行 → 缺陷"的顺序排列，供评审查阅。

- 本目录是测试文档正本；分析过程、内部核对清单、执行计划、接口验证步骤等中间材料不放入。
- 文档之间靠编号互相引用，文件名保持稳定；改名会使 `02`、`03` 中的引用失效。
- 阶段三用例的正文在 `04-测试用例.md`（当前状态：v1.0，2026-11-09 定稿）；飞书多维表格为执行与维护副本，导入快照不随公开仓库发布。

## 三、编号规则

| 前缀 | 所在文档 | 含义 | 范围 |
|---|---|---|---|
| TC-xx | `02` | 测试关注点 | TC-01～TC-39 |
| Q-xx | `02` §4.1 | 待确认项及核对状态 | Q-01～Q-16；阶段二补充的 Q-17 见 `03` §3.4 |
| A-xx | `02` §4.2 | 实现现状（代码核对所得的事实） | A-01～A-16 |
| B-xx | `02` §4.3 | 已确认的业务口径 | B-01～B-07 |
| X-xx | `02` §4.4 | 清单外发现（需求缺口或风险线索） | X-01～X-04 |
| REQ-xx | `03` §3.2 | 需求项索引 | REQ-01～REQ-22 |
| TP-xx | `03` §1 | 测试点 | TP-01～TP-32 |
| D-xx | 缺陷记录表、附录 | 已确认缺陷 | D-01～D-22 |

规则：

- 编号一经定稿即冻结，不复用、不重排、不合并不同含义；新增项从当前最大号 +1。
- 跨文档引用写法：`02 §4.3 B-05`、`03 §3.4`、`原文 6.1`、`附录 D-02`；`02`、`03` 是文件名简写。
- `03` 中的 TP 编号、短名与顺序必须与清单、Mermaid 导图、Xmind 导图完全一致，改一处就要同步全部。

## 四、引用来源规则

- **需求依据只能引 `需求规格说明.md`** 的章节或附录；`测试计划.md` 只支撑范围、目标与配置基线，不能当作需求条款。
- `02`、`03` 中的"实现依据"只写到**模块级**（如"后端欠款计算""前端表单校验与提交"），不列文件名与行号，避免把代码位置带进需求文档。
- 实现事实不等于需求：`02` §4.2 的 A 类记录现状，`02` §4.4 的 X 类记录差异与风险，二者都不能反向改写需求或预期。
- 不引用本目录之外的材料，不补造需求条款；材料没写清的，记为待确认或需求缺口，不按缺陷处理。
- 实现与需求不一致 → 记 `D-xx`；需求本身没定义 → 记"需求缺口"（如 B-03 允许负库存），不生成缺陷。

## 五、版本规则

- `v0.x`：草稿，允许改内容与编号；`v1.0`：定稿，编号、短名、顺序冻结，只接受文字勘误并记入修订记录。
- 每份文档头部写明版本、日期与输入；`02` 的修订记录保留到当前版本。
- 版本说明：`02` v1.0 在 v0.4 基础上把代码位置引用改为模块级说明，并补一条 v1.0 修订记录；`03` v1.0 内容未改，只把对 `02` 的版本引用更新为发布版。
- 同步顺序：改本目录 → 复核一致性（TP 集合、导图、编号、引用）→ 导入飞书。

## 六、范围与配置基线

**测试范围**：需求规格说明 §二～§九 + 附录，包括建单与单号、保存与校验、状态流转、删除、库存、权限、金额与欠款、异常提示。

**不在范围**：采购订单关联与分批入库、财务凭证与应付、多级审批、序列号/批号/多单位的完整链路（各保留 1 条针对性验证）、商品档案维护、修正欠款的业务功能（只验证其按钮受编号 1 控制）、性能、安全渗透、并发。

**配置基线**（执行前必须核对）：

- 强审核开启、更新单价关闭、其余开关关闭；
- 零收付款开关默认关闭；
- 换配置后库存类结论会相反，`03` 的 TP-21、TP-22 依赖此基线。

**判定原则**：预期以 `需求规格说明.md` 为准；附录中的差异按"应然 vs 实现"判定，不因当前实现改写预期。

  - `02`、`03` 的结论只相对于本次提供的完整原文与阶段一分析结果，范围外功能未验证。
